## Rôle
Deux choses distinctes regroupées dans ce package (thème commun : accès/droits) :
1. **Aidants de proximité (SOS)** : une case à cocher par aidant, décochée par défaut, qui décide qui reçoit le SOS.
2. **Droits d'accès interface Aidant** : bitmask JSON par aidant (🔧 config / ⚙️ messages / 📅 calendrier / 📺 vidéo / 📷 photos / 🚨 alertes), édité depuis `config.html` → Sécurité, appliqué automatiquement selon l'identité réelle de connexion.

### 1. Aidants de proximité
- **Coché** = l'aidant fait partie des « aidants de proximité » → reçoit le SOS.
- **Décoché** (valeur par défaut) = ne reçoit pas le SOS, seulement les alertes modérées/infos (tous les aidants les reçoivent, cochés ou non).
- Modifiable à tout moment depuis le dashboard Configuration, sans YAML, sans redémarrage (juste « Recharger la configuration YAML » si l'entité elle-même vient d'être ajoutée/modifiée ici).

⚠️ Les 7 `person.x` associés sont des **comptes FICTIFS** confirmés par l'utilisateur le 2026-08-05 — à remplacer par les vrais comptes/entity_id une fois les vrais aidants inscrits dans HA.

### 2. Droits d'accès (`input_text.m10_droits_aidants`)
JSON compact `{ "<object_id_person>": <bitmask>, ... }`, max 255 caractères (limite `input_text`). Bitmask :

| Bit | Icône | Droit |
|:----|:------|:------|
| 1 | 🔧 | config — accès à `config.html` lui-même |
| 2 | ⚙️ | messages — réglages M03 |
| 4 | 📅 | calendrier — accès à `calendrier.html` |
| 8 | 📺 | video — accès à `video.html` |
| 16 | 📷 | photos — accès à `photos.html` |
| 32 | 🚨 | alertes — reçoit les alertes modérées/infos (**distinct** du SOS — système `input_boolean.m10_proximite_aidant_*` non lié, décision explicite de l'utilisateur) |

Cases combinables (ex : `5` = config + calendrier). `person.eric` (installateur) a **toujours tous les droits**, détecté via `is_owner`/`is_admin` dans la réponse WebSocket — jamais lu depuis ce JSON, jamais modifiable ici. Édité depuis `config.html` → Sécurité (`buildDroits`, `loadDroits`, `saveDroits`, `toggleDroit`).

⚠️➡️✅ **Correctif sécurité 2026-08-15** : `buildDroits()` affiche `person.attributes.friendly_name` (donnée HA réelle, modifiable en direct par n'importe quel compte ayant accès à HA). Injecté dans `innerHTML` sans échappement jusqu'ici — trouvé lors d'un audit sécurité externe (Hermes), vérifié indépendamment. Corrigé : `escHtml()` appliqué à `${name}`.

### 3. Application des droits par identité réelle (WebSocket `auth/current_user`)
**Construit et déployé le 2026-08-15.** Remplace les 2 PIN construits plus tôt le même jour (`m10_pin_pages_dediees`, `m10_pin_config`) — retirés car jugés ingérables par l'utilisateur : *"le pin c'est ingerable dans le sens que si un aidant donne son pin a un autre aident il auras acces"*. Un PIN partagé ne distingue pas les personnes ; les droits ci-dessous s'appliquent selon **qui est réellement connecté**, pas selon un secret partageable.

**Mécanisme** (identique dans `config.html`, `calendrier.html`, `video.html`, `photos.html`) :
1. Il n'existe pas d'endpoint REST HA pour "qui suis-je" (`/api/profile` est mort — voir Pièges #10). Seul le **WebSocket** le permet.
2. `wsCurrentUser(token)` : connexion à `/api/websocket`, séquence `auth_required` → envoi du token → `auth_ok` → envoi `{id:1, type:"auth/current_user"}` → réponse `{id, name, is_admin, is_owner}`.
3. `resolveAccess()` : si `is_admin`/`is_owner` → accès total. Sinon, cherche dans `/api/states` le `person.*` dont `attributes.user_id === id` (cette correspondance a été vérifiée en direct : le `id` WebSocket égale exactement `person.eric.attributes.user_id`). Si trouvé, lit le bitmask correspondant dans `input_text.m10_droits_aidants` (clé = object_id de la personne). Si aucun `person.*` ne correspond (compte HA existe mais pas rattaché à une fiche Personne), retourne un accès nul.
4. Chaque page vérifie son bit propre au chargement (`config`=1, `calendrier`=4, `video`=8, `photos`=16) et affiche soit le contenu (`#app-content`/`#page-content`), soit un écran « Accès refusé » explicite dans le gate (`#access-gate`).

⚠️ **Prérequis bloquant** : un aidant sans compte HA propre (nom d'utilisateur + mot de passe, Paramètres → Personnes → Autoriser la connexion) **ne peut pas être identifié** — `resolveAccess()` retourne alors `mask:0` et l'accès est refusé, même si des droits sont cochés dans `config.html` pour son `person.*`. Sur l'instance live, **seuls 2 aidants sur 7 ont un compte réel** aujourd'hui (`person.eric`, `person.aidant_1_admin_ok` = "Anîs") — voir Pièges #11.

⚠️➡️✅ **Trou de sécurité réel trouvé et corrigé (2026-08-15, suite)** : signalé par l'utilisateur — *"ANAIS a le droit de modifier les messages alors que rien est coché"*. Vérifié : l'icône ⚙️ (Paramètres messages) dans `aidant.html` faisait `showScreen('settings')` sans **aucune** vérification, ni ce jour-là ni avant. Contrairement à 🔧/📅/📺/📷 (qui ouvrent des pages séparées, chacune protégée par son propre gate), l'écran Paramètres est un simple changement d'écran interne à `aidant.html` — il n'a jamais existé de contrôle dessus. Le droit "⚙️ messages" du bitmask était donc **décoratif depuis l'origine**, avant même cette session. Corrigé : la même logique WebSocket `auth/current_user` a été dupliquée dans `aidant.html` (`resolveAccess()`, `hasDroit()`), calculée une fois au chargement (`refreshAccessUI()`), qui (a) cache les 5 icônes/boutons (⚙️🔧📅📺📷) tant que le droit n'est pas résolu ou absent, ET (b) bloque l'action elle-même dans chaque fonction `open*()` — pas seulement l'affichage, pour ne pas dépendre uniquement d'un bouton caché.

✅➡️⚠️➡️✅ **`?only=tv` — faille corrigée (2026-08-15, suite, audit sécurité #3)** : la première version faisait `unlockGate()` sans **aucune** vérification en mode `only=tv`, en supposant que `video.html` était le seul chemin d'accès possible — jamais vérifié. Un accès direct par URL (`/local/config.html?only=tv`) donnait donc accès à `init()` en entier (droits, réglages, visio…), le mode `only-tv` ne masquant que visuellement via CSS — les fonctions (`toggleDroit`, `saveDroits`, `saveText`…) restaient appelables via la console quel que soit l'affichage. Trouvé par un audit sécurité externe (Hermes), vérifié indépendamment (code relu, confirmé exact). Corrigé : `runAccessGate()` vérifie désormais le droit 📺 video (bit 8) en mode `only=tv`, au lieu de 🔧 config — exactement le droit déjà requis par `video.html`, donc plus de raccourci possible par URL directe.

Pour comparaison, les panneaux HACS et Outils Dev natifs de HA sont déjà `require_admin: true` en natif (vérifié via `get_panels`) — seul ce panneau ajouté manuellement au projet avait l'oubli.
14. 🟢 **Observation non corrigée (15/08, suite)** : le panneau `browser-mod` (liste des navigateurs connectés) est également `require_admin: false`, mais c'est réglé en dur par le composant `browser_mod` lui-même, pas configurable depuis `configuration.yaml` — risque faible (juste informatif, pas de modification de config possible depuis ce panneau), non traité.
